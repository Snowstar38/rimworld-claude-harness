## 1. Rotation IS reachable from the bridge. Proven live, then removed.

`Designator_Place.placingRot` is `protected` — reflection required. Read from the
installed `Assembly-CSharp.dll`, `Designator_Build.CanDesignateCell` compiles to
`GenConstruct.CanPlaceBlueprintAt(entDef, c, placingRot, Map, godMode, …, StuffDef, …)`,
so **the dry-run oracle has always been rotation-dependent** and has been silently
answering for one fixed rotation.

Positive control that it is genuinely honoured: a four-rotation sweep of `Cooler`
at (113,146) returned **four different sentences** — `north` "Identical blueprint
already exists here", the other three "Space already occupied". Distinct answers
are the falsifiability that clicking the Q/E buttons never had.

## 2. The sandstone chunk at (114,145) was innocent, for two sessions

Sweeping that cell: north/south → *"Both the hot and cold sides of the cooler must
be exposed."* **east and west → accepted.** East puts cold at (113,145) (inside)
and hot at (115,145) (outdoors).

The refusal blamed on a boulder was a **rotation refusal from a tool that could not
rotate**. The cell also takes the cooler *as* the wall, so one building closes the
breach that a separate wall blueprint was being built for. The chronicle's plan
from three sessions ago was correct; nothing could execute it.

## 3. Which cooler face is which, derived from the game's own code

`Building_Cooler.TickRare` computes `loc0 = Position + South.RotatedBy(Rotation)`
and `loc1 = Position + North.RotatedBy(Rotation)`, then does
`loc0.GetRoom(Map).Temperature += ControlTemperatureTempChange(…)` and
`GenTemperature.PushHeat(loc1, …)`.

> **COLD = Position + IntVec3.South.RotatedBy(Rotation)**
> **HOT  = Position + IntVec3.North.RotatedBy(Rotation)**

`IntVec3Utility.RotatedBy` case 0 is `ldarg.0; ret`, so **north is the identity**.

**Unverified in game:** the two *coordinates* are certain, but the cold/hot
*labels* rest on reading `set_Temperature` as cooling and `PushHeat` as heating.
Nobody watched a built cooler and measured it with `map.py rooms --cold`. Do not trust the
labels until someone does.

## 4. Q and E are real, and unreachable

The rotation buttons exist as clickable UI, captioned `Q` and `E`, in an
ImmediateWindow that **only draws while the Architect main tab is open** —
selecting a designator through the capability API is not enough to make it appear,
which is why every previous session missed them. Clicking them resolves cleanly

## 5. — there is no way to read rotation back

`get_designator_state` carries no rotation field (diffed across a click: only
timestamps and operation ids move). A 147 KB dump of the whole capability registry
has **zero** matches for "rotat". `home/list_buildings` returns `rotation: None` on
blueprints.

**This is the deeper deficit**: not that we cannot set rotation, but that we cannot
see it — which makes every rotation experiment unfalsifiable.

## 6. Scripting is a dead end for this

`rimbridge/run_lua`, `run_lua_file` and `run_script` lower to a **10-statement JSON
mini-language** (call / let / set / if / foreach / while / assert / fail / print /
return) that can only invoke registered capabilities plus arithmetic. **No
reflection, no field access**, so it cannot reach `placingRot`. Worth knowing
before anyone else spends a turn on it.

## 7. No key-send exists anywhere

All 134 tools enumerated. The only input-shaped ones are `press_accept`,
`press_cancel`, `scroll_ui_target`, `drag_cell` and the three `click_*`. No generic
key send, no hotkey, no rotation argument on any placement tool.

## The zone double-claim (M's error log)

```
Stockpile zone 2 overwriting slot group square (113, 0, 145) of Stockpile zone 1
Verse.Log:Error → HaulDestinationManager:SetCellFor → AddHaulDestination → Zone:CheckAddHaulDestination
```

Confirmed in `Player.log` and `Player-prev.log`: it fires **exactly twice, at load
time**, once each for (113,145) and (113,144) — not continuous spam. Both logs are
otherwise clean, no exceptions.

Matching state, found independently by a Scout: `list_zones` reports 5 zones
totalling 61 cells; a per-cell read of all 62,500 map cells finds **59** zoned
cells. **"Stockpile zone 1" claims `cellCount` 2 and owns no cell anywhere**; those
two cells belong to "Stockpile zone 2". Two zone objects, one square.

**Suspected cause — UNVERIFIED, the check was stopped before it finished.**
`upstream\Source\RimWorldArchitect.cs` ~234-250 calls
`explicitTargetZone.AddCell(cell)` **directly** when a zone is the designator
target, bypassing `Designator_ZoneAdd.DesignateSingleCell`. The hypothesis is that
the designator path removes a cell from its current owner first and the bare
`AddCell` does not, so our own automation created the overlap — last session did
~30 cells of stockpile zoning through exactly this path. **This was never confirmed
against the IL.** Do not record it as the cause until someone reads `Zone.AddCell`
and `Designator_ZoneAdd.DesignateSingleCell`.

**Whether it is harmful is also unresolved.** `Verse.Log.Error` calls
`TickManager.Pause()` — that is already why `Faction.OfPlayer` was purged from every
companion file. Firing twice at load is probably harmless; nobody proved it.

**The fix, if one is wanted:** a companion tool that does what the game does —
remove the cell from its current owner, then add, and **name what it took from
whom** in the response. The current path corrupts silently precisely because
nothing ever says that. Deleting the zero-cell phantom zone is the likely repair.
**Not built. Not attempted.**

## Resolution — 2026-09-02, dedicated workshop session (Fable 5.1, with two Opus 5 subagents)

Every claim above was checked against the game's decompiled code or the running
game before anything was built on it. What held, what didn't, what was done:

- **1, 4, 5 (rotation unreachable, unreadable):** held. Fixed by going around the
  designator entirely: `home/place_building` calls `GenConstruct.CanPlaceBlueprintAt`
  with the rotation as a parameter, sweeps all four by default, places with the
  same wipe-then-place sequence the architect menu uses, and `home/list_buildings`
  now carries `rotation` on every row. Wrapper: `build.py`. The Q/E buttons are
  clickable now too (`ui.click('E')` — they are `icon_button`s and the old kind
  filter excluded them), but nothing can read the result back, so `build.py` is
  the path.
- **2 (the chunk was innocent):** held, re-proven live twice: north/south refused
  with the exposed-sides reason, east/west accepted. The chunk is reported as
  "haul first" — a blueprint does not wipe an item; the builder carries it out.
  **A cooler blueprint now stands at (114,145) facing East** (cold face 113,145
  inside, hot face 115,145 outdoors): 90 steel, 3 components.
- **3 (which face is which):** held, from `Building_Cooler.TickRare` read in
  ILSpy rather than by hand: cold = Position + South rotated, hot = Position +
  North rotated. The tool prints both faces per rotation with outdoors/indoors
  and temperature. *Still not measured on a built cooler* — none is built.
- **6, 7 (scripting, key-send):** not re-checked; moot once placement bypasses
  the designator.
- **Zone double-claim — cause CONFIRMED, mechanism exact.** `Zone.AddCell` only
  overwrites the grid pointer and never tells the old owner; the game's own
  `Designator_ZoneAdd.DesignateMultiCell` never moves a cell between zones (it
  skips any cell with `ZoneAt != null`); the bridge's upstream shortcut
  (`RimWorldArchitect.cs` ~246, `explicitTargetZone.AddCell` on cells
  `CanDesignateCell` accepted, which includes same-type-zoned cells) is the only
  path that produces the state. `Zone.Delete()` would have cleared zone 2's
  grid cells, so the repair edits the phantom's list (public in 1.6) and skips
  the slot-group notify that would itself `Log.Error`. **Repaired live:** zone 1
  deregistered, 59/59 consistent, no new error line. `home/zone_cells` also does
  add / remove / create / delete the game's way and names `takenFrom`. Wrapper:
  `zones.py`. Harm of the original bug: two error lines at load and a pause if
  pause-on-error is on — nothing more was found.
- **Storage:** `zones.py` is the instrument that measures space (cells under a
  building / holding items / free, per zone). On this save the colony has **two**
  real stockpile cells (113,144-145, full) plus two dumping zones. Not zoned in
  this session — where the pantry goes is a play decision.
- **The cold room:** the instruments now agree with M. `list_buildings`
  shows the research bench at (110-112, 144-145) filling six of the eight cells
  the chronicle called the cold room; `place_building` shows (113,145) as
  *outdoors* because (114,145) is an open breach. A bench room with two
  stockpile cells and a hole, not a cold room.
- **Smaller instrument findings:** wrong-pawn — cause (b), Luna read the alert
  list as a roster; one sentence added to `look.py`'s prompt, the Scout brief in
  `rota.py`, and a READ NARROWLY line in `verify.py`. Saves location — PLAYBOOK
  note; `setup.py` already read the profile folder. Debug-log window — excluded
  from `letters.dialog_window()` on both paths, verified with the log open.
  Two-tools-disagree-on-the-hour — `setup.py` did tick arithmetic without the
  map's longitude (-19.5°); it now uses `home/get_time` and labels any fallback
  as tick arithmetic; verified 01h == 01h. `rim.py tools` follows every page
  (137 names) and takes `--grep`. `rimbridge/` namespacing — PLAYBOOK note.
  `ui.click('E')` — fixed as above. `rim.game` returning a str for
  `get_cells_plus` — **not reproduced** (oversize rects come back as a proper

  Butcher-spot `0x` bill and campfire without bills — not chased; play items.
